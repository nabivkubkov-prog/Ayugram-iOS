# Проверка AyuGram iOS на устройствах

Это план ручной проверки, а не отчёт об успешном тестировании. На момент добавления документа подписанное приложение на iPhone не запускалось. Успешные Foundation-тесты проверяют модели и правила; они не доказывают работу MTProto, уведомлений, интерфейса или подписи.

В отчёте для каждого пункта необходимо записать commit приложения, номер сборки, модель iPhone, версию iOS, время, шаги, наблюдаемый результат и статус: **PASS / FAIL / NOT RUN / UNSUPPORTED**. Любой пункт без фактического запуска остаётся NOT RUN.

## Подготовка

1. Установить подписанную сборку проверяемого commit на iPhone. Убедиться, что bundle ID соответствует provisioning profile, приложение запускается после перезагрузки устройства и не падает при возвращении из фона.
2. Использовать два собственных тестовых аккаунта: **A** в проверяемом iOS-приложении, **B** в официальном Telegram на другом устройстве. Все сообщения ниже отправляются только между ними или в созданных для проверки группах/каналах.
3. Закрыть остальные активные клиенты аккаунта A на время сетевых проверок: их online/read-события иначе искажают результат. Не завершать чужие сеансы и не использовать чужие сообщения.
4. Создать обычный личный чат A↔B, приватную группу с A и B, публичную тестовую группу, приватный и публичный тестовые каналы. B должен иметь права на публикацию и удаление тестовых сообщений. При проверке тем создать отдельную тему в форумной группе.
5. Подготовить небольшие файлы с известным содержимым: JPEG, MP4, PDF, аудиофайл, голосовое сообщение, стикер. Для каждого записать имя и размер; для точной проверки сохранённых файлов использовать SHA-256.
6. Перед каждым сценарием фиксировать положения переключателей. Обновлять приложение между этапами только с сохранением commit/версии в отчёте.

## Призрак и события сервера

| ID | Шаги | Ожидаемый результат |
| --- | --- | --- |
| G-00 | Выключить все функции призрака. B отправляет текст; A открывает чат, печатает и отправляет ответ. | В B видны штатные read/typing/online-события. Это контрольный опыт, подтверждающий пригодность окружения. |
| G-01 | Включить запрет прочтения. B отправляет новый текст; A открывает чат, прокручивает, открывает медиа, закрывает и снова открывает чат. | Локальный счётчик A может очиститься, но B не получает прочтение от этого устройства. Проверить личный чат, группу и канал отдельно. |
| G-02 | При G-01 переключить A в другой чат и перезапустить приложение. | Накопленные локальные прочтения не отправляются автоматически после перезапуска. |
| G-03 | При G-01 выполнить явную команду прочтения на сервере для выбранного чата. | Прочтение отправлено ровно для выбранного чата. Общая настройка призрака остаётся включённой; другой чат не прочитан. |
| G-04 | Включить запрет typing. A вводит текст, записывает голосовое/видео и загружает большой файл. | B не видит соответствующих событий активности. Проверить личный чат и группу. |
| G-05 | Включить запрет online, открыть A и оставить приложение активным. Затем отправить обычное сообщение и повторить с отложенной отправкой призрака. | Записать фактически наблюдаемый статус у B в каждом режиме. Обычная отправка может раскрыть активность через сервер; отсутствие явного online-запроса не считается доказательством полной невидимости. |
| G-06 | Включить восстановление offline. Отправить текст, фото, альбом, реакцию; повторить после редактирования своего сообщения. | После каждого поддерживаемого действия состояние возвращается offline в наблюдаемом интервале. Зафиксировать кратковременные появления online, если они есть. |
| G-07 | B публикует новую историю. A включает скрытие просмотров и открывает её; затем повторить с выключенной настройкой на другой истории. | С включённой настройкой этот просмотр отсутствует в списке B; контрольный просмотр появляется. Нужен реальный список просмотров у B, а не только локальный значок. |
| G-08 | Настроить исключения «всегда читать» / «никогда читать» для разных чатов при одинаковых глобальных настройках. | Сетевое поведение соответствует исключению каждого чата; исключения не действуют на другие аккаунты. |
| G-09 | Включить прочтение при отправке / реакции / голосовании по отдельности. | Прочтение появляется только от разрешённого вида взаимодействия. Обычный просмотр всё ещё не отправляет его. |
| G-10 | Настроить различные политики для аккаунтов A и второго тестового аккаунта в том же приложении; переключаться и перезапускать приложение. | Индивидуальные политики остаются различными. В явно выбранном глобальном режиме политики становятся общими. |
| G-11 | Включить призрак, заблокировать одну из его опций, выключить и снова включить общий переключатель. | Заблокированная опция не меняется; остальные следуют общему переключателю. |
| G-12 | При отложенной отправке отключить сеть, отправить текст/альбом, вернуть сеть; отдельно отменить запланированное сообщение. | Нет дубликатов, повреждённых альбомов и отправок после успешной отмены. Проверить сохранение явного silent/scheduled выбора пользователя. |

## Удаления и история правок

| ID | Шаги | Ожидаемый результат |
| --- | --- | --- |
| H-00 | Выключить сохранение удалённых. B отправляет и удаляет новый текст. | Сообщение удаляется обычным образом; новая запись архива не создаётся. |
| H-01 | Включить сохранение удалённых. A получает текст B, затем B удаляет его у всех. | У A остаётся пометка «удалено» и отдельная запись в Архиве сообщений с правильными chat/message ID, автором и временем. |
| H-02 | Повторить H-01, затем восстановить сетевое соединение и перезапустить приложение, чтобы повторно получить difference/update. | Повторное серверное удаление не стирает сохранённое сообщение и не создаёт дубликат записи. |
| H-03 | Включить историю правок. B отправляет `v1`, затем меняет на `v2`, затем на `v3`, дожидаясь доставки каждой версии A. | Контекстное меню → «История AyuGram» показывает `v1` и `v2` только данного сообщения; основной чат показывает `v3`. |
| H-04 | A сам отправляет `mine-v1` и меняет на `mine-v2`. | Предыдущая версия сохраняется до локального применения ответа edit API, а не только при следующем серверном update. |
| H-05 | B меняет только жирное/курсивное форматирование без изменения текста. | Создаётся revision snapshot с отличающимися entities. Браузер пока отображает простой текст; полное rich-text-воспроизведение не объявляется реализованным. |
| H-06 | Создать одинаковые числовые message ID в разных каналах и разных аккаунтах, затем отредактировать/удалить сообщения. | Архив не смешивает namespace, peer, message и account ID. Открытие истории из контекстного меню показывает только выбранное сообщение. |
| H-07 | Удалить сообщение самостоятельно через штатное меню A. | Явное удаление пользователя выполняется штатно; архивный hook не отменяет удаление и не восстанавливает сообщение на сервере. |
| H-08 | Получить и удалить сообщение внутри темы, ответ на сообщение, пересланное сообщение и часть альбома. | Snapshot сохраняет topic/thread, grouping, reply attributes и forward metadata. Текстовая JSON-копия сохраняет эти поля. |
| H-09 | Открыть архив, искать по тексту, Unicode без учёта регистра, автору, чату и message ID. | Поиск находит соответствующие записи, постраничное отображение добавляет следующие 100, открывается полный прокручиваемый текст без интерпретации Markdown сообщения. |
| H-10 | На A выключить сеть/завершить процесс. B отправляет и удаляет сообщение до доставки A. Вернуть A в приложение. | Приложение не выдумывает отсутствующий текст. Этот сценарий не считается поддерживаемым восстановлением неполученного сообщения. |
| H-11 | Повторить на секретном чате и сообщении с таймером. | В текущей реализации эти сообщения исключены из архива. Это явный разрыв с частью Android-функций, а не PASS переноса TTL. |

## Вложения, долговечность и ошибки

| ID | Шаги | Ожидаемый результат |
| --- | --- | --- |
| M-01 | A полностью загружает JPEG/MP4/PDF/голосовое/стикер без текстовой подписи; B удаляет сообщение. | Создаётся запись даже при пустом тексте. Загруженный ресурс сохраняется отдельно от медиакэша; доступен через «Открыть / поделиться вложениями». Возможность просмотра конкретного формата зависит от установленного обработчика. |
| M-02 | Сохранить доступные вложения через share в Files и сравнить SHA-256 с исходниками. | Байты основного загруженного файла совпадают. Для фотографий отметить фактически загруженное разрешение: приложение не обещает наличие оригинала, если скачана только меньшая версия. |
| M-03 | После M-01 очистить весь медиакэш Telegram, перезапустить приложение и открыть архив. | Текст и сохранённые файлы остаются доступны. Удаление приложения или данных аккаунта — отдельное действие, не очистка медиакэша. |
| M-04 | Отключить автоматическую загрузку. A видит сообщение с незагруженным файлом, B удаляет его. | Метаданные остаются, вложение честно показано недоступным; не выдаётся битый cache-path за сохранённый файл. |
| M-05 | B заменяет медиа в уже загруженном сообщении. | История старой версии открывает старый ресурс; новая версия не перезаписывает архивный файл. |
| M-06 | Выбрать лимит 256 MB. Сохранить несколько файлов суммарно больше лимита; отдельно файл больше лимита. | Старые retained-файлы освобождают место; текстовые записи не удаляются. Один слишком большой файл остаётся недоступным в архиве. |
| M-07 | Выключить сохранение медиа только для публичных групп, оставив текст и приватные группы включёнными. | Политики текста и файлов различаются; приватная группа не наследует запрет публичной. |
| M-08 | В отладочной сборке искусственно отказать `linkItem`/`copyItem` или исчерпать доступное место. | Сообщение и метаданные сохраняются; UI показывает недоступное вложение. Основной Telegram update не падает. |
| M-09 | В отладочной сборке остановить процесс после создания retained-файла, но до commit Postbox. Перезапустить и открыть архив. | Непривязанный файл очищается механизмом ремонта; файлы существующих записей сохраняются. Если запись архива не декодируется, автоматическая очистка не гадает о её файлах. |
| M-10 | Смоделировать отказ удаления одного retained-файла, затем очистить найденные записи архива. | Появляется сообщение об ошибке; запись с не удалённым файлом остаётся для повторной попытки. Другие аккаунты и основной Telegram-чат не затрагиваются. |
| M-11 | Заполнить тестовыми fixtures архив до 20 000 записей либо 64 MB метаданных. | Новые snapshots останавливаются с видимым сообщением о ёмкости. Старые записи не исчезают автоматически. После export/clear новые записи снова принимаются. |
| M-12 | Открыть архив с 1 000 / 10 000 / 20 000 записей и выполнить поиск, прокрутку, удаление и импорт. | Измерить время и peak memory в Instruments. Наличие ограничения не доказывает достаточную производительность; неприемлемая задержка считается FAIL. |

## Правила и JSON-копии

| ID | Шаги | Ожидаемый результат |
| --- | --- | --- |
| P-01 | В режиме «сохранять все» добавить чат в исключения и выполнить удаление/правку в нём и в другом чате. | Первый чат не создаёт новые snapshots, второй создаёт. Уже сохранённые записи не удаляются сменой политики. |
| P-02 | Включить «только выбранные» с пустым списком, затем добавить один чат. | Пустой список ничего не сохраняет и это видно в UI. После добавления сохраняется только выбранный чат. |
| P-03 | Изменить правила bot dialogs / bot messages in groups и типы публичных/приватных групп/каналов. | Каждое правило проверяется отдельно; личные сообщения человека не блокируются bot-настройкой. |
| P-04 | Экспортировать найденные записи в JSON и импортировать обратно в тот же аккаунт. | Число дубликатов не увеличивается; текст, большие 64-bit IDs, entities/media snapshots, timestamps и forward metadata не теряются. Файлы вложений не входят в JSON и импорт не обещает их восстановление. |
| P-05 | Импортировать JSON аккаунта A в другой аккаунт приложения. | Импорт отклоняется до изменения архива. |
| P-06 | Импортировать повреждённый JSON, неизвестную version, повторяющиеся record IDs, файл больше 32 MB, а также JSON с `../../` в имени retained-файла. | Ошибка или безопасная очистка supplied-пути согласно формату; нет crash, записи произвольных файлов и доступа к другому аккаунту. |
| P-07 | Импортировать корректный файл в почти полный архив. | Приложение сообщает фактическое число добавленных записей и состояние ёмкости; оно не заявляет, что импортировало всё, если достигнут предел. |

| B-02 | Войти с собственными Telegram API ID/hash, проверить код входа, 2FA, повторный запуск и восстановление сессии. | Реальная авторизация проходит. Заглушечные credentials в compile-only сборке не считаются проверкой входа. |
| B-03 | Проверить входящий текст/звонок при активном приложении, в фоне и после блокировки экрана. | Уведомления и звонки проверяются с действующими APNs/capabilities. Отсутствие ключей не маскируется как ошибка архива. |
| B-04 | Повторить основные G/H/M сценарии на минимально поддерживаемой iOS и актуальной iOS; отдельно iPad для popover/share/menu. | Корректная навигация, отсутствие crash и видимость всех действий. |

## Функции, которые этот набор проверок не превращает в реализованные

- Полное соответствие конкретной APK-сборке 2026 года: её точный публичный source commit не установлен.
- Архивирование TTL/одноразовых сообщений и секретных чатов.
- Автоматическая загрузка недостающих файлов архива с разными Wi-Fi/cellular лимитами.
- Импорт/экспорт собственных SQLite-баз Android/Desktop AyuGram и текущая совместимость с AyuSync.
- Богатое воспроизведение всех типов исходных сообщений внутри архива; сейчас snapshots хранят attributes/media, а браузер отображает текст и предоставляет файлы отдельно.
- Получение сообщений, которые сервер удалил до доставки клиенту, либо постоянная Android-подобная фоновая служба на iOS.
- Серверные преимущества Premium, которых нет у используемого аккаунта.

Для AyuForward, Local Premium, Message Shot, Streamer mode и прочих дополнительных функций нужны отдельные сценарии после появления конкретных call sites. Строка настройки или наличие исходного ресурса не является доказательством работающей функции.
